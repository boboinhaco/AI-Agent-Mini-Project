## 1부. 무엇을 고쳤고 결과가 어땠나 (2분)

### 1-1. 이 에이전트가 하는 일 (20초) **[화면: README.md 맨 위 "1. 이 에이전트가 하는 일" 표]**

이 에이전트는 한마디로 **서버 운영팀의 AI 당직자**입니다. 운영자가 "결제 서비스가 느려요"라고 말하면,
사람이 하듯이 모니터링 화면을 보고, 최근 로그를 읽고, 회사 대응 매뉴얼을 찾아서 "지금 상태는 이렇고 이렇게
조치하세요"라고 보고합니다.

### 1-2. 개선 전에 뭐가 문제였나 (30초) **[화면: README.md "4. Before" 표, before/screens/ollama_uc3_two_systems.png]**

코드를 고치기 전에 같은 질문 10개를 먼저 돌려서 기록해 뒀습니다. 세 가지가 심각했습니다.
- "느려요", "디스크가 부족해요" 같은 말을 **장애가 아니라 잡담으로 분류**해서 아무 조사도 안 했습니다.
- 두 서버를 말해도 **첫 번째만 조사**했고, CPU 문제인데 **DB 다운 매뉴얼**을 골랐습니다.
- 한 질문에서 작은 모델이 5분간 답이 없자 **서버 전체가 죽어서** 다음 질문까지 끊겼습니다.

### 1-3. 무엇을 했나 (40초) **[화면: README.md "5. 무엇을 바꿨나" 표]**

고친 것 네 가지와 더한 것 세 가지입니다.
- **고친 것**: ① 한 파일에 뭉친 코드를 역할별로 나눴고, ② 매뉴얼 고르는 방식을 키워드 규칙에서 **RAG, 즉 뜻으로
  검색하는 방식**으로 바꿨고, ③ 장애 문의를 제대로 알아보게 했고, ④ 답변이 **조사한 숫자를 실제로 인용했는지
  코드가 검사**하게 했습니다.
- **더한 것**: ⑤ 조사 담당을 **메트릭·로그·매뉴얼 전문 에이전트 셋**으로 나눠 동시에 돌리고, ⑥ 재시작·롤백 같은
  위험한 조치는 **사람이 승인 버튼을 눌러야** 진행되게 했고, ⑦ 대화가 길어지면 과거를 요약해 기억하게 했습니다.
  거기에 단위 테스트 40개, LLM이 답변을 채점하는 평가, 인시던트 리포트 저장까지 넣었습니다.

### 1-4. 결과 (30초) **[화면: doc/images/metrics_capture.png]**

같은 질문 10개를 다시 돌린 결과입니다.
- 정확도 체크가 fake 백엔드에서 **22%에서 100%**, 실제 모델에서 **83%에서 100%**가 됐습니다.
- **서버 오류 2건이 0건**이 됐습니다.
- 대신 지연시간과 비용은 두 배 정도 늘었습니다. 검증이 실제로 답변을 반려해서 다시 쓰게 하고, 로그 조회가
  추가됐기 때문입니다. 정확도와 안정성을 얻는 대신 치른 비용이고, 숨기지 않고 보고서에 적었습니다.

## 2부. 코드 설명 (3분)

### 2-1. 그래프 구성 — "작업 흐름도" (1분) **[화면: doc/images/graph_after.svg → agent/graph.py]**

먼저 그림부터 보겠습니다. 에이전트는 **공장 컨베이어 벨트**처럼 단계를 거칩니다. 라우팅 → 계획 → 게이트 →
조사 → 재계획 → 분석 → 작성 → 승인 → 검증 → 확정입니다. 아래로 돌아가는 선 세 개가 핵심인데, **"부족하면
다시 조사", "거절하면 다시 작성", "검증 불합격이면 다시 작성"**입니다. 한 번에 끝내는 게 아니라 스스로 고치는
구조입니다.

**[agent/graph.py 45~78줄]** 이 그림이 코드로는 이 함수 하나입니다.
- 48~58줄 `add_node`: 벨트 위에 작업대를 하나씩 놓는 부분입니다. 52줄을 보시면 `research`만 다르게
  `build_research_subgraph`를 꽂습니다. **작업대 하나 자리에 작은 공장 하나를 통째로 넣은 것**입니다.
- 61~73줄 `add_conditional_edges`: 갈림길입니다. 예를 들어 73줄은 "검증이 합격이면 확정으로, 아니면 작성으로
  돌아가라"입니다.
- 78줄 `compile(checkpointer=MemorySaver())`: 승인 기능 때문에 필요한 **중간 저장**입니다. 사람이 승인 버튼을
  누를 때까지 멈춰 있다가 그 자리에서 이어가려면 상태를 저장해 둬야 합니다.

**[agent/subgraphs/research.py 152~164줄]** 작은 공장의 설계도입니다. `dispatch`에서 세 에이전트로 갈라지고
`merge`에서 다시 합쳐집니다. 162~163줄의 반복문이 그 갈라짐과 합침입니다. 31~32줄의 `Annotated[list,
operator.add]`가 중요한데, **세 명이 동시에 결과를 적어도 서로 덮어쓰지 않고 목록에 "추가"만 되게** 하는
장치입니다.

**[agent/nodes/approval.py 56줄]** 사람 승인은 이 한 줄, `interrupt()`입니다. 여기서 그래프가 멈추고, 서버가
운영자의 승인/거절을 받아 `Command(resume=...)`으로 다시 깨웁니다.

### 2-2. MCP — "에이전트가 쓰는 공용 도구함" (1분) **[화면: mcp_server.py → agent/mcp_client.py]**

MCP는 쉽게 말해 **AI가 외부 도구를 쓰는 표준 규격**입니다. USB처럼, 어떤 도구든 같은 방식으로 꽂아 쓸 수 있습니다.

**[mcp_server.py 34~85줄]** 도구함 쪽입니다. 세 종류가 있습니다.
- 34줄 `@mcp.tool()` `get_monitoring_status`: **지금 수치를 재는 도구**입니다. 부를 때마다 값이 달라집니다.
  62줄 `get_recent_logs`는 이번에 제가 추가한 **최근 로그를 가져오는 도구**입니다.
- 70줄 `@mcp.resource("runbook://…")`: **책장에서 매뉴얼 꺼내기**입니다. 주소로 문서를 찾습니다.
- 79줄 `@mcp.prompt()`: **진단할 때 따라야 할 표준 절차서**입니다. 계획 단계가 이걸 받아서 할 일을 정합니다.

**[agent/mcp_client.py 53~59줄, 86~95줄]** 에이전트 쪽입니다.
- 53~59줄 `start`: 서버가 켜질 때 도구함 두 개(ops, docs)를 **별도 프로세스로 한 번만** 띄우고 계속 재사용합니다.
- 86~95줄 `find_resource_template`: 중요한 부분입니다. "매뉴얼이 어느 도구함에 있는지"를 코드에 박아 두지 않고,
  **연결된 도구함을 차례로 물어봐서 가진 쪽을 찾은 뒤에** 요청합니다. docs 서버는 일부러 넣은 가짜인데, 이걸
  제대로 건너뛰는지 확인하는 용도입니다.

조사 서브그래프의 세 에이전트가 각각 이 도구들을 부릅니다: 메트릭 에이전트는 수치 도구, 로그 에이전트는 로그
도구, 매뉴얼 에이전트는 책장입니다.

### 2-3. RAG — "뜻으로 매뉴얼 찾기" (1분) **[화면: agent/rag.py → agent/nodes/replan.py]**

개선 전에는 알림 문구에 "cpu"가 있으면 CPU 매뉴얼, 이런 **단어 맞추기 규칙 9줄**이었고, 아무 단어도 안 걸리면
무조건 DB 다운 매뉴얼로 갔습니다. RAG는 **문서를 숫자 좌표로 바꿔서 질문과 가장 가까운 문서를 찾는 방식**입니다.
비유하면 도서관 사서가 제목 글자가 아니라 내용의 뜻으로 책을 찾아 주는 것입니다.

**[agent/rag.py]**
- 126~139줄 `build`: 서버가 켜질 때 매뉴얼 6개를 읽어 좌표로 바꿔 벡터 저장소에 넣습니다. 각 문서에는
  "이건 디스크 매뉴얼이다" 같은 꼬리표(metadata)를 붙입니다. 임베딩할 때 절차 본문이 아니라 **제목과 증상
  부분만** 넣는데, 절차 문장은 매뉴얼끼리 비슷해서 오히려 헷갈리게 하기 때문입니다.
- 109~116줄 `make_embeddings`: 좌표로 바꾸는 모델을 백엔드에 따라 고릅니다. 테스트용 fake는 모델 없이 글자
  조각으로 계산하고, 로컬은 nomic-embed-text, OpenAI는 text-embedding-3-small입니다.
- 150~158줄 `classify`: 검색 결과 상위 몇 개를 가져온 뒤 **"증상 어휘가 질문에 얼마나 겹치나"로 한 번 더
  줄을 세웁니다.** 실제로 써 보니 로컬 임베딩 모델이 한국어에 약해서 "디스크 공간이 부족해요"를 CPU 매뉴얼로
  고른 적이 있었고, 이 재정렬을 넣고 8케이스 모두 맞게 됐습니다.

**[agent/nodes/replan.py 41줄]** 이 검색을 부르는 자리입니다. 1차 조사가 끝났는데 매뉴얼이 없으면,
"사용자 질문 + 저하된 서버의 알림 문구"를 검색어로 넣어 매뉴얼을 고르고 그걸 추가 조사 작업으로 올립니다.
22줄은 시스템명이 없는 문의일 때 쓰이는데, 전체 서버를 한 번 훑은 뒤 **질문의 증상과 맞는 서버만 남기는**
선별에 같은 검색을 씁니다.

## 예상 질문과 답

- **Q. 지연이 두 배 늘었는데 괜찮나요?** — 운영 장애 대응에서는 틀린 답을 빨리 주는 것보다 맞는 답을 1분 늦게 주는
  쪽이 낫다고 판단했습니다. 그리고 늘어난 시간 대부분은 검증이 반려해서 다시 쓰는 시간이라, 모델이 처음부터 잘
  쓰면 줄어듭니다.
- **Q. 승인 기능이 매번 뜨면 귀찮지 않나요?** — 재시작·롤백 같은 되돌리기 어려운 조치가 있을 때만 뜹니다. 조회만
  하는 답변은 그냥 통과합니다. 환경변수로 끌 수도 있습니다.
- **Q. 데이터가 가짜 아닌가요?** — 맞습니다. monitoring.json과 logs.json은 샘플입니다. MCP 도구 안의 코드만
  실제 모니터링 API 호출로 바꾸면 나머지는 그대로 동작합니다.
- **Q. 테스트는 실제 모델 없이 어떻게 돌리나요?** — `tests/conftest.py`에 가짜 MCP와 결정론 LLM을 넣어 그래프
  전체를 3초 안에 돌립니다. 의존성 주입 덕분에 가능합니다.
